# 007 — What is safe to publish, and how sharing is gated

Parent: `../MAP.md`
Label: `wayfinder:grilling` (HITL)
Blocked by: 004
Status: CLOSED 2026-08-18

## Question

Define the rule that decides which entries and which fields leave the machine.

The hazard is concrete. Skill descriptions and names carry client identities and personal
material: `daily-reflection`, `morning`, `intentional-buy`, `week-wrap`, `sunday-timeblock`,
plus client-named content inside descriptions. Usage counts also leak what Eli actually works on.

Must decide:

1. Allowlist or blocklist. Recommendation to argue against: allowlist only, since a blocklist
   fails silently every time a new personal skill is added.
2. Whether the allowlist lives in the sidecar, a separate file, or as a per-skill flag.
3. Which *fields* are stripped on publish even for allowlisted skills. Usage counts are the
   obvious candidate.
4. Whether the published artifact is a filtered snapshot generated by a second command, or the
   same snapshot with the UI hiding things. It must be the former; confirm and record why.
5. Whether plugin skills are published at all, given they are not Eli's to share.

## Resolution

Resolved 2026-08-18. All five questions answered. The architecture 005 landed already carries
the field this ticket needs, so the decision is mostly about defaults and about what leaves
the machine, not about new machinery.

### 1. Allowlist only. Fail closed.

An entry is published only if something says so explicitly. Nothing is published by omission.

The measurement settles the argument the ticket asked for. A deliberately crude regex over the
descriptions of the 169 global and repo skills, matching only `Eli`, `Obsidian`, `vault`,
`personal`, `Highland`, and `client`, flags **33 of 169**. That is a floor, not a ceiling: it
catches `daily-reflection`, `intentional-buy`, `morning`, `client-intake` and `client-handoff`,
and it misses anything that names a client without using the word "client". A blocklist would
have to be right about all 169 and stay right on every skill added afterwards, and it fails
open every time it is wrong. An allowlist fails closed, and a skill Eli forgot to allowlist is a
missing row, not a leak.

Today `publishable` is `false` on all 426 entries, so the publish command currently emits an
empty library. That is the correct starting state.

### 2. The allowlist lives in `data/overrides.json`, keyed on `id`, as `publishable: true`.

Already implemented — `scan.py` reads `publishable` from the override record and it merges last.
No new file, no new field.

The two rejected homes matter:

- **Not the sidecar.** `sidecar.json` is regenerated by the LLM pass. An allowlist that lives
  there is silently reset by a routine refresh, which is a leak-by-maintenance.
- **Not per-skill frontmatter.** The tool is read-only with respect to `SKILL.md` by decision 1
  of the map. Marking a skill publishable is not a reason to break that.

### 3. Fields stripped on publish, even for allowlisted entries

Removed from every published entry:

- **The entire `usage` object.** Counts, timestamps, states, sources. Usage says what Eli
  actually works on and how often, which is the most sensitive thing in the snapshot and is
  useless to a teammate.
- **Absolute paths** — `path`, `skill_file`. They carry the username and the machine's layout,
  and the local hand-off-to-editor action has no meaning on someone else's machine.
- **`author` when `author_source` is `assumed`.** 005 flagged 85 entries that default to Eli by
  assumption. Publishing an assumption as a byline is fabricating provenance.
- **Drift and local-state fields** — `also_in_repo`, `repo_differs`, `is_symlink`,
  `upstream_url` where it points at a private repo.

Removed from the snapshot envelope: `roots`, `usage_sources`, `orphan_usage`, `scan_errors`.
All four describe Eli's machine.

Kept: `id`, `name`, `description`, `version`, `updated_at`, `domain`, `domain_secondary`, `kind`,
`category_source`, `category_status`, `orchestration_class`/`_verdict`/`_source`, `body_lines`,
`has_resources`, `schema_version`, `snapshot_generated_at`.

**Delegation edges are filtered to the published set, and the removed ones are counted, not
named.** A published `design-sprint` whose targets are private must not name them, and must not
read as a leaf either. So edges to unpublished entries drop and `delegates_to_withheld: N`
remains. Same principle 006 settled for Q12, applied across a trust boundary instead of a filter.

### 4. A second command writing a separate filtered file. Confirmed.

`publish.py` (or a `--publish` flag on the existing writer) reads `skills.json` and writes
`data/public.json` containing only allowlisted entries with the stripped fields absent. The UI
hiding things is not an option and never was: the snapshot is a static JSON file served next to
the page, so anything the UI hides is one view-source away. Hiding is presentation; publishing
is a data boundary. Recorded explicitly because it is the kind of shortcut that looks harmless.

The cost is low for the reason 005 predicted: it is the same writer with an entry filter and a
field denylist.

### 5. Plugin skills are not published. Global and repo skills only.

They are not Eli's to share, a teammate gets them by installing the same plugin, and the set of
installed plugins is itself information about how the team works. This drops 257 of 426 entries
before the allowlist is even consulted, which also means the allowlist only ever has to be
maintained over Eli's own 169.

### Downstream effects

- **006 (UI):** the published page renders `public.json` with the same code path. Any column
  bound to `usage` must degrade to absent rather than to zero, or the published view reads as
  "nothing here has ever been used". This is the one UI change the publish path forces.
- **008 (refresh):** publishing is a manual, deliberate act. It must never be wired to the same
  trigger as the routine scan.
- **The map's "how teammates consume this" open question is still open** and is not blocked by
  this ticket. This decides what may leave; it does not decide that anything should.

## Amendment — 2026-08-18, same day: the sharing model was wrong

Eli corrected the premise the ticket was built on. Sharing does not mean teammates read a
published snapshot of his library. **It means teammates get the app and the scanner, and run
them against their own `~/.claude` to see their own skills.**

The resolution above is not withdrawn — it is correct about what may leave the machine if
anything ever does — but it is **no longer on the critical path**, and the ticket's framing of
"the hazard is concrete" now applies to a different hazard.

### What changes

1. **The deliverable is the tool, not the data.** `scan.py` plus one HTML file. Each person's
   snapshot is generated locally and never travels. This is strictly safer than the allowlist,
   because zero of Eli's entries leave the machine rather than a hand-audited subset.
2. **The allowlist and `public.json` become dormant, specified but unbuilt.** `publishable`
   stays in the schema, defaulting false, and everything above stands as the spec for the day
   someone actually wants a published view of Eli's own library. Nothing is built for it now.
3. **This closes the map's "how teammates consume this" question.** The answer is: they run the
   scanner themselves. Not a published snapshot, not a merged view.

### The new hazard, which is real and is the opposite of the old one

Distributing the tool means distributing a repo, and `data/skills.json` in that repo is a
1.0 MB file containing every one of Eli's skill descriptions, absolute paths, and usage counts.
**The generated data must not ship with the tool.**

- `data/*.json` is gitignored, or the repo carries an empty `data/` and the README's first step
  is running the scanner. Shipping a populated `data/` is exactly the leak the allowlist existed
  to prevent, arriving through the back door.
- A first-run empty state is required: the app opened before any scan says "run `python3
  scan.py`" rather than rendering a broken page or, worse, someone else's library.

### Portability, now a first-class requirement rather than an accident

`scan.py` is already `os.path.expanduser("~")`-based for six of its seven roots, so it mostly
works on another machine unchanged. Gaps to close:

- **`REPO_ROOT` hardcodes `~/Development/claude-skills`**, which is Eli's alone and contributes
  2 of 426 entries. Make it optional — skip silently when absent — or drop the repo source.
- **Every input must be allowed to be missing.** A teammate may have no plugins, no
  `~/.agents/.skill-lock.json`, no `history.jsonl`, and a shorter transcript window. Each
  absence must degrade to an empty list and a recorded note, never a crash. `scan_errors` and
  `usage_sources` already exist to carry that.
- **Usage coverage differs per machine.** 002's three-state rule already handles this: a
  teammate with a two-week-old `history.jsonl` gets `coverage: "transcripts_only"` and
  `no_data` rather than a page full of false "never used" accusations. Verify this holds when
  `history.jsonl` is young, not just when it is absent.
- Dependencies stay Python 3 plus PyYAML. Nothing new.

Status: CLOSED 2026-08-18, amended same day. Publish path specified and deferred; sharing model
is tool distribution.
